# 재보충 계산: 수요에서 원재료 구매 후보까지

현재 구현은 실제 ERP 데이터를 일관된 스냅샷으로 읽고, 주문 이력·다단계 BOM·가용 재고·공급 조건을 연결한다. 실행 권한을 검증하는 계산 API와 불변 계획 저장도 연결했다. 계산만으로 ERP 발주나 재고를 변경하지 않는다. [실행 연결 안내](13_execution_and_plan_api.md)에 계획 버전·멱등·완료 검증을 설명한다. 실제 모델 실행과 승인·발주 적용은 후속이다.

## 계산 흐름

```mermaid
flowchart LR
    ERP[주문·LOT·입고·생산·공급 조건] --> Snapshot[수량·추적 관계 대사]
    Snapshot --> Forecast[요일별 수요 / 확정 주문 잔량]
    Forecast --> BOM[날짜별 생산·다단계 BOM]
    BOM --> Net[LOT·예정 입고 차감]
    Net --> Supplier[MOQ·배수·납기·인증 비교]
    Supplier --> Result[원재료 구매 후보와 근거]
```

- `PlanningSnapshotRepository`는 REPEATABLE_READ 이상에서 정책·관련 ERP 행을 읽는다. 상위 트랜잭션이 더 낮은 격리 수준이면 거부한다. 근거에는 정렬된 원본 행 참조와 계산에 사용한 필드가 포함된다.
- `ForecastService`는 기준일 직전 최대 56일의 CONFIRMED/SHIPPED 주문을 요일별로 평균 낸다. 최소 28일의 수집 이력을 요구하고 수집 시작 전의 날을 0으로 가정하지 않는다.
- 같은 날짜의 예측과 미출고 확정 주문은 큰 값 하나를 사용한다. 과거 납기 미출고는 오늘 수요로 옮기고, 납기일이 없는 잔량은 오류로 남긴다. 여러 주문 상세에 같은 제품이 있어도 출고량은 주문·제품별로 한 번만 차감한다.
- 기본 기간은 30일, 안전재고는 요일별 평균을 다시 평균 낸 7일분이다. 안전재고는 마지막 날의 목표 재고이며 매일 수요에 반복 가산하지 않는다. 예측의 중간 평균과 수량은 소수 6자리 올림을 사용한다.
- `BomPlanner`는 제품·필요일을 노드로 만들고 해당 날짜의 유효 BOM을 적용한다. 공유 반제품의 상위 수요를 모은 뒤, 같은 품목의 이른 필요일부터 재고를 차감한다. 부모 납기가 늦어도 긴 리드타임 때문에 자재가 먼저 필요할 수 있다.
- 생산량은 배치 단위로 올림한다. 잉여분은 생산 완료 예정일부터 다음 수요에 사용하고 제품 소비기한이 지나면 제외한다. 생산 착수가 이미 과거라면 가능한 계획처럼 표시하지 않는다.
- `SupplierSelectionService`는 자재별 남은 총량을 첫 부족일까지 확보하는 구매 후보를 비교한다. 날짜별 재고/예정 입고 차감 이후 자재별 MOQ와 주문 배수를 한 번 적용한다. 단가가 아니라 실제 주문 수량을 반영한 총액, 도착일, 공급처 ID, 조건 ID 순으로 선택한다.
- 필요한 인증은 주문 시점에 발급되어 있고 도착일까지 유효해야 한다. 30일 이내 만료는 검토 정보로 반환한다. 적격 공급처가 하나라도 없는 계산은 NEEDS_ATTENTION이며 전체 금액을 확정하지 않는다.

KG/G, L/ML, EA, CASE를 지원한다. CASE와 EA는 포장 구성 없이 서로 환산하지 않는다. 환산율은 단위 차원과 일치해야 하며 구매 수량·기본 수량·단가가 NUMERIC(18,6)에 정확히 저장될 수 없으면 후보에서 제외한다. 금액은 행별 KRW 원 단위 HALF_UP이다.

## 실제 데이터의 대사

| 연결 | 확인하는 조건 |
|---|---|
| 출고 → 출고 LOT | LOT 배분 합계 = 출고 수량, 제품·확인된 창고 일치 |
| 생산 LOT → 출고/반제품 사용 | 최초 수량 − 출고 − 하위 생산 투입이 음수가 아님 |
| 제품 LOT → stock | 모든 상태의 LOT 잔량 합계와 창고별 실재고 일치 |
| 입고 → 원재료 LOT | 모든 분할 LOT 최초 수량 합계 = 입고 수량, 자재·공급처·발주 상세 연결 일치 |
| 원재료 LOT → 생산 투입 | 최초 수량 − 투입 합계 = remaining_quantity |
| 발주 상세 → 입고 | received_quantity = 기록된 입고량, 미입고 잔량의 납기 확인 |

대사 후 가용량을 계산할 때 QUARANTINE/RECALLED·만료 제품 LOT과 RELEASED가 아닌 원재료 입고를 제외한다. 물리 재고가 있다는 사실과 생산에 사용할 수 있다는 사실은 구분한다. 위치가 불명확한 양수 제품 LOT은 다른 창고의 재고로 추측하지 않는다.

예정 발주는 실제 재고와 별도 출처로 표시한다. 기한이 지난 미입고·납기 미지정·계획 기간 이후 입고는 사용 가능한 예정 공급에 포함하지 않는다. 아직 입고되지 않은 PO에 실제 LOT을 요구하지는 않는다.

## 예시 데이터와 기대 결과

[Fixture 설명](../database/seed/replenishment_demo_README.md)과 [SQL](../database/seed/replenishment_demo.sql)은 **마이그레이션만 적용한 빈 폐기용 DB**에서 먼저 실행한다. 이후 실제 데모용 사용자와 외부 신원을 연결한다. SQL은 기존 사용자·업무 데이터가 있으면 거부하며 이를 삭제하거나 덮어쓰지 않는다.

| 계산 | 손계산 결과 |
|---|---|
| AMR | 수요 60 + 안전 14 − 가용 30 = 부족 44 → 생산 50 CASE |
| BSC | 수요 30 + 안전 7 − 가용 15 = 부족 22 → 생산 30 CASE |
| 공유 반죽 | 19 − 가용 4 = 생산 15 KG |
| 밀가루 | 9 − 가용 3 − 예정 입고 2 = 순소요 4 KG → MOQ 반영 구매 5 KG |
| 설탕 | 6 − 가용 1 = 구매 5 KG |
| 포장재 | 80 − 가용 20 = 구매 60 EA |
| 구매 후보 금액 | 밀가루 6,000 + 설탕 7,500 + 포장재 3,000 = 16,500원 |

전체 fixture 통합 테스트는 위 결과와 계산 전후 ERP 거래의 불변을 검증한다. 낮은 단가지만 MOQ 때문에 총액이 더 높은 대안도 함께 반환한다.

## 구현 경계와 검증

Flyway V19와 독립 DDL11은 수량·가격 정밀도, 단위, BOM, 공급 조건, 반제품 사용, 계획 저장 구조를 추가한다. 새 NUMERIC 컬럼은 NaN을 거부한다. 기존 FK·양수·잔량 범위 제약을 유지하며, BOM의 겹치는 활성 버전·같은 날짜의 순환과 동시 편집도 거부한다.

달력상 유효한 BOM이어도 날짜별 재고 차감 순서와 제조 의존성이 서로 순환하는 재작업 계획은 `PLANNING_DEPENDENCY_CYCLE`로 반환한다. 이는 데이터의 BOM 순환과 구별되는 현재 계획기의 지원 경계다. 그런 입력을 임의로 풀어 과잉 구매안을 만들지 않는다. 유한 생산능력 최적화·여러 거점의 자원 배분·시간을 넘나드는 재작업 최적화는 첫 데모에 포함하지 않는다.

계산 코어 단계의 검증 결과: PostgreSQL 18.6의 빈 DB에서 `clean test bootJar` 328개 통과(실패·오류·skip 0). 독립 DDL/fixture와 V17→V19 업그레이드·모호한 창고의 제한적 backfill·동시 BOM 순환 거부도 확인했다. 당시 MCP는 소수·큰 정수의 원본 숫자 문자열을 보존하며 15개 테스트가 통과했다. 이후 계획 저장·실행 연결 검증은 [실행 연결 안내](13_execution_and_plan_api.md)를 따른다. 실제 Auth0·대화 클라이언트 로그인 인수는 보류(#21·#22)이며 이 결과에 포함되지 않는다.
