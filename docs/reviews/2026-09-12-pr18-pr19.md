## 검토 범위와 방법

Astra 검토자 3명이 독립 검토 후 한 차례 근거 대조를 수행했다. 처음 확인하지 못한 파일은 후속 담당을 나눠 읽었다. 전체 변경의 직접 작성한 실행 코드·스키마·시드·MCP·CLI·실행기·설정/데모 도구를 합산 범위로 검토했다. 세 명 모두 모든 파일을 독립적으로 검토했다는 뜻은 아니다.

- #18: 인터페이스의 서비스·컨트롤러·DTO·매처, V8~V17과 대응 DDL, 기본 등록, MCP와 설정.
- #19 Backend: 인증·권한, 계획 계산과 전체 snapshot 정합성 조회, 구매 제안/결정/검증, lease·실행·복구, 대화 조회/답변, 디스패치, 후속 책임, 생성된 스키마를 사용하는 저장소.
- #19 기타: Zig CLI, Node 실행기와 Docker 설정, MCP 전체 도구·인증·전송, Auth0 설정/readiness/E2E 스크립트와 대응 테스트·문서, V18~V25 및 대응 DDL/fixture.
- 바이너리·생성 코드·lockfile 본문은 수동 리뷰 대상에서 제외했다. 의존성 설치와 고정 실행 이미지의 실제 빌드는 별도로 검증했다. 모든 테스트 fixture·문서의 모든 문장을 독립 리뷰한 것은 아니다.

| 실행 환경 호환성 | 고정 Codex 0.151.0이 실제 Astra 요청을 버전 오류로 거절 | 0.154.0으로 고정 버전·lock·이미지 참조 갱신. 실제 호출은 버전 오류를 넘었으나 워크스페이스 크레딧 부족으로 종료 |

`RunCompletionPolicy` 추출은 역할별 완료 근거와 실행 상태 전이를 분리한다. 완료 검증 → 후속 책임 → lease 재확인 → 상태 변경 → 종료 이벤트 순서를 유지했다. claim/savepoint/복구 흐름은 다시 설계하지 않았다.

종료 Case와 관련한 신규 동시 종료 시나리오를 별도로 실행한 것은 아니다. 잠금 순서는 코드로 검토했고 기존 동시성·트랜잭션 테스트를 포함해 전체 Backend를 실행했다.

## 실제 인수의 남은 조건

실제 데모용 DB는 시험 DB와 분리하여 V25·fixture·알레르겐 22종까지 준비했다. PostgreSQL·Zig·CLI·Docker·실행 이미지·전용 볼륨의 readiness 설치/조회 항목은 통과했다. 외부 신원·활성 인간·Case·Run은 생성하지 않았다. 실제 비밀 설정은 저장소 밖 보호된 파일에만 있다.

1. Auth0 로그인 및 개발 tenant 선택, 실제 OBO/worker/client grant 설정과 MANAGER·VIEWER 신원 연결.
2. ChatGPT·Codex의 실제 OAuth 연결/갱신. ngrok 로그인·기존 고정 HTTPS 주소·실제 전달 검증은 완료했다.
3. 사용 가능한 Astra 워크스페이스 크레딧. 이후 실제 역할 실행·native 분석 분담·승인 대기 종료를 관찰.
4. ChatGPT → Codex 새 대화 → ChatGPT 및 반대 방향의 업무 연결, 버전/hash별 인간의 개별 승인·거절·취소 UX.
5. 실제 PO·감사·후속 WAITING 확인. 생산·입고를 만들어 Case를 자동 종결하지 않음.

실행 절차는 [데모 실행서](../15_demo_runbook.md)를 따른다. 이 조건이 남아 있는 동안 #19의 전체 데모 완료를 선언하지 않는다.
