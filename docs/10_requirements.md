# Mulino Coreano 요구사항 정의서

## 1. 무엇을 만드는가

**한국에서 식품을 생산·판매하는 가상 기업을 위해, 구매·재고·품질 업무를 기록하고 AI에게 맡긴 업무가 사람의 승인과 외부 회신을 거쳐 끝까지 이어지도록 하는 ERP + AI 업무 관리 시스템을 만든다.**

Mulino Bianco의 한국 진출을 가정한 SAP 컨설팅 포트폴리오다. 글로벌 업무 구조를 한국 운영 조건에 맞게 설계하는 능력과 AI의 업무 수행을 통제하는 능력을 보여주는 것이 목적이다. 실제 브랜드와의 연계나 실제 SAP 제품 구축을 의미하지 않는다.

사용자는 다음 세 가지 일을 할 수 있어야 한다.

1. **확인한다:** “이 제품 재고가 얼마나 있고, 무엇이 부족한가?”
2. **맡긴다:** “이 기간에 이 제품이 품절되지 않도록 조치해줘.”
3. **살핀다:** “내가 알아야 할 위험과 지금 판단해야 할 일을 확인한다.”

시스템은 그 사이의 데이터 조회, 근거 정리, 담당 배정, 대기, 재개, 처리 이력을 맡는다. 업무 완료 여부는 실제 결과로 확인한다.

사용자가 느껴야 할 핵심 경험은 **“원하는 결과를 맡기면 담당이 계속 처리하고, 나는 진행과 근거를 확인하면서 내 판단이 필요한 부분에 참여한다”**이다. 사용자는 ERP 처리 순서나 에이전트 실행 구조를 먼저 배울 필요가 없어야 한다. 세 가지 사용자 모드는 ASK / ACT / MONITOR이며, 승인·반려는 이 흐름 안에서 이루어지는 인간의 판단이다.

## 2. 해결할 문제와 기대 효과

아래 문제는 실제 고객 인터뷰 결과가 아닌 가상 업무 시나리오의 가정이다.

| 현재 업무에서 가정하는 문제 | 시스템에 요구하는 변화 | 확인할 결과 |
|---|---|---|
| 재고·발주·입고 자료를 따로 확인해야 한다 | 관련 정보를 연결해 조회한다 | 재고 또는 LOT에서 관련 거래까지 확인 가능 |
| 부족을 발견한 이후 누가 처리하는지 불명확하다 | 목표별 담당 업무와 대기 사유를 남긴다 | 모든 미완료 업무의 책임 또는 미배정 예외가 보임 |
| 공급사 회신이나 승인 뒤 후속 조치를 놓친다 | 관련 이벤트로 해당 업무를 재개한다 | 동일 업무를 새로 접수하지 않고 이어서 처리 |
| AI 제안을 믿을 근거가 부족하다 | 사실·추론·증거·인간 결정을 구분한다 | 제안에서 근거 자료와 판단 범위 확인 가능 |
| AI가 잘못된 발주·품질 상태 변경을 할 수 있다 | 변경 전 역할별 승인과 변경 이력을 요구한다 | 미승인 변경이 반영되지 않음 |
| 품질 문제 발생 시 영향 범위 확인이 어렵다 | 원재료부터 출고 고객까지 양방향 추적한다 | 대상 LOT의 원인과 영향 거래처 확인 가능 |

## 3. 사용자와 책임

| 사용자 | 주요 업무 | 필요한 결과 |
|---|---|---|
| 운영 담당자 | 재고 조회, 목표 등록, 진행 확인 | 현재 상태·담당·다음 조치 |
| 구매 관리자(MANAGER) | 발주안 검토 및 승인·반려 | 수량·거래 조건·근거·영향 |
| 품질 담당자(QC) | 입고 이상과 알레르겐 검토 | 이상 근거·대상 입고·처리 결정 |
| 관리자(ADMIN) | 리콜 승인, 운영 정책 관리 | 영향 범위·승인 대상·처리 이력 |
| 조회 사용자(VIEWER) | 허용된 업무 정보 조회 | 변경 권한 없는 조회 |

AI 역할은 공급망·구매·품질관리와 이를 조정하는 Orchestrator로 나눈다. 공급망은 부족이나 위험을 찾아 구매에 연결하고, 구매는 발주안을 준비하며, 품질관리는 품질 이상에 대한 조치를 제안한다. 권한이 필요한 최종 변경은 지정된 인간 승인자가 결정한다.

## 4. 업무 범위와 경계

### 4.1 전체 목표 범위

공급업체·원자재 등록 → 발주 → 입고 → 원재료 LOT → 생산 투입 → 생산 LOT → 수주·출고 → 고객까지 연결한다. 창고·재고·품질 이상·리콜·승인 이력을 함께 관리한다.

운영 모델은 **한국 내 생산·판매**로 확정했다. 완제품 부족을 생산 필요량과 원재료 소요량으로 연결하며, 완제품 직접 수입·구매는 첫 데모에서 제외한다.

### 4.2 첫 완결 데모 범위

**완제품 부족 확인 → 재보충 목표 등록 → 생산 필요량·다단계 BOM 기반 원재료 소요량 계산 → 공급처 비교·원재료 발주안 → MANAGER 승인 또는 반려 → 승인된 발주 반영 → 결과 확인**을 첫 번째 완결 흐름으로 구현한다.

이 흐름 하나에서 ERP 조회, AI 역할 분담, 업무 지속성, 인간 승인, 실제 데이터 변경을 함께 보여줄 수 있다. 목표 이름은 “품절 방지”로 표현할 수 있지만, 이 데모의 완료 조건은 **승인된 발주의 정상 등록**이다. 실제 입고 전까지 품절 방지 목표 자체를 달성했다고 표시해서는 안 된다.

데모에는 재현 가능한 주문 이력·다단계 BOM·복수 공급처 예시 데이터를 사용한다. 초기 데이터는 seed로 준비하며 마스터 관리 화면은 제외한다. 실제 업무 실행은 Codex를 먼저 지원하고, 인간은 Auth0로 인증된 원격 MCP를 통해 ChatGPT와 Codex 양쪽에서 같은 업무를 조회·승인한다. 세부 계약과 검증 순서는 [구현 계획](superpowers/plans/2026-09-05-replenishment-demo.md)을 따른다. 이 범위 확정은 현재 구현 완료를 의미하지 않는다.

**구현 대조 결과:** 현재 재고 조회는 완제품(`products`) 대상이지만 발주 상세는 원재료(`raw_material_id`)만 참조한다. 이 간극은 생산 필요량·원재료 소요량 계산을 추가해 연결하기로 했다. 현재 구조로 완제품 수량을 그대로 발주할 수 있다고 가정하지 않는다.

### 4.3 후속 범위

- 인증서 만료 감지와 입고 통제
- 알레르겐 정보 검증 및 온도 이탈 처리
- 양방향 LOT 조회와 리콜 승인 흐름
- 공급사 회신 수신, 인간 이메일 발송 이후 자동 재개
- 사용자용 대시보드와 Slack 등 채널 연결
- 재고·발주·입고를 계속 관찰하는 장기 목표 운영

### 4.4 첫 데모에서 제외할 범위 — 제안

실제 SAP 연동, 회계 결산·급여, 실거래 결제, 실제 세금계산서 발행, 식약처 실전송, 통관 시스템 연동, 전체 ERP 입력 화면, 임의 질문을 모두 처리하는 분석 기능은 포함하지 않는다. 기존의 관련 데이터 필드는 유지한다.

## 5. 대표 사용자 시나리오

### S-01 재고 확인

운영 담당자가 제품명 또는 SKU로 재고를 조회한다. 시스템은 제품·창고별 수량을 반환하고, 조회 실패와 재고 0을 구분한다. 이 질문만으로 새 업무를 만들지 않는다.

### S-02 재보충 업무 위임

운영 담당자가 대상 제품, 목표 기간과 원하는 결과를 등록한다. 시스템은 업무 식별자를 만들고 담당을 배정한다. 공급망 역할은 재고와 수요 근거를 확인하고 부족량을 산정한다. 데이터가 부족하면 필요한 정보를 명시하고 확인되지 않은 수량을 확정값처럼 사용하지 않는다.

구매 역할은 발주안을 준비한다. 구매 관리자는 공급업체·수량·조건·판단 근거를 검토한다. 승인 시 허용된 변경을 한 번 반영하고, 반려 시 발주를 실행하지 않고 사유를 남긴다. 반려 이후 수정할지 종결할지는 업무 정책에 따른다.

### S-03 대기와 재개

공급사 회신이나 사람의 판단이 필요하면 대기 사유와 재개 조건을 저장한다. 시스템을 다시 시작하거나 대화가 끝나도 이 상태를 잃지 않는다. 관련 회신 또는 결정이 도착하면 해당 업무만 재개하고 최신 상태를 다시 확인한다.

### S-04 품질 이상과 추적

품질 담당자가 문제 원재료 LOT를 선택하면 영향을 받은 생산 LOT와 출고 고객을 확인한다. 완제품 LOT에서 원재료와 공급업체로 역추적할 수도 있다. AI는 근거와 조치안을 준비하고 입고 변경은 QC, 리콜 및 RECALLED 변경은 ADMIN 승인을 거친다.

## 5.1 UX 목표와 수용 기준

아래 항목은 사용자 경험 목표를 검증 가능한 요구사항으로 정리한 것으로, 현재 구현 완료를 뜻하지 않는다. 첫 데모 적용 범위는 §9, 채널별 확장은 §4를 따른다.

| ID | 사용자가 경험해야 할 것 | 수용 기준 | 연결 기능 |
|---|---|---|---|
| UX-01 | 질문하고, 목표를 맡기고, 주의할 일을 살핀다 | ASK와 MONITOR는 Case를 만들지 않는다. ACT는 관련 기존 업무를 찾거나 새 업무를 접수하고 목표를 보여준다 | FR-01·02·10·19 |
| UX-02 | 원하는 결과를 말하면 시스템이 처리 계획을 구성한다 | 사용자가 에이전트 선택·Work Item 작성·ERP 명령 순서를 지정하지 않아도 담당과 다음 조치가 정해진다. 추가 정보에 따라 계획을 조정한다 | FR-03·04·05 |
| UX-03 | 대화가 끝나거나 채널을 바꿔도 같은 일이 이어진다 | 새 대화 또는 다른 지원 채널에서 동일 Case의 목표·결정·대기 상태를 불러온다. 과거 경위를 다시 입력하거나 채널별 업무를 중복 생성하지 않는다 | FR-02·08·17 |
| UX-04 | 누가 무엇을 처리하고 무엇을 기다리는지 알 수 있다 | 업무 상세에 목표, 현재 상황, 역할별 조치, 대기 대상·조건, 필요한 결정, 근거, 주요 이력을 표시한다 | FR-03·08·10·11 |
| UX-05 | 필요한 순간에 구체적인 판단만 요청받는다 | 요청마다 인간이 필요한 이유, 확인된 내용, 남은 질문, 추천안, 미조치 영향을 제공한다. 일상적인 조회·도구 호출 알림으로 사용자를 중단하지 않는다 | FR-06·10·19 |
| UX-06 | 승인하거나 발송한 뒤에도 담당이 후속 업무를 이어간다 | 승인·Send 이후 사용자에게 “계속해”나 재접수를 요구하지 않는다. 담당과 남은 의무를 유지하며 관련 업무를 재개한다 | FR-06·08·09·18 |
| UX-07 | 제안의 이유를 묻고 대안을 비교할 수 있다 | “왜 600개인가?”, “300개만 사면?”에 산식·가정·출처와 결과 차이를 설명한다. 비교 요청만으로 발주를 변경하지 않는다 | FR-04·05·07·11 |
| UX-08 | 현재 값의 출처와 불확실성을 확인할 수 있다 | 설명에서 자료 출처·관측 시각·이전 값·변경 이유·영향 업무를 확인한다. 미확인 또는 충돌한 정보는 확정 사실과 구분한다 | FR-11 |
| UX-09 | 정정과 판단이 다음 대화에도 반영된다 | 정정 내용을 증거 확인과 관련 상태 갱신에 연결한다. 답변의 적용 범위를 표시하고 일회성 결정을 다른 업무의 일반 정책으로 확대하지 않는다 | FR-11·17 |
| UX-10 | 요청하기 전에 위험과 필요한 판단을 알아차린다 | MONITOR에서 판단 필요·위험·처리 중·외부 대기·최근 해결을 구분하고 관련 업무로 연결한다. 정상 대기는 위험과 별도로 표시한다 | FR-10·19 |
| UX-11 | 필요한 분석을 대화에서 요청할 수 있다 | 지원 데이터 범위에서 요청한 보고서를 생성하고 기준 시점·근거를 제공한다. 보고서가 사라져도 ERP 사실·업무·증거·결정은 유지한다 | FR-01·11 및 후속 분석 기능 |
| UX-12 | 업무 결과를 중심으로 진행과 완료를 이해한다 | 일반 업무 화면은 실행 ID·토큰·도구 로그 없이 이해 가능하다. 대기는 계속 실행 중인 것처럼 표시하지 않고, 완료는 실제 검증 결과와 남은 목표를 함께 설명한다 | FR-09·10·12 |

### 5.1.1 채널별 경험

| 채널 | 사용자 목적 | 제공할 경험 |
|---|---|---|
| ChatGPT / Claude | 질문·분석·목표 위임·검토 | 현재 업무 맥락을 불러와 근거 탐색, 이유 설명, 대안 비교, 제안 수정, 승인, 자율 처리 내역 확인을 지원한다 |
| Slack | 중요한 변화 인지와 짧은 판단 | 업무 영향과 필요한 결정을 간결하게 제시하고 승인·검토·반려 또는 상세 확인으로 연결한다 |
| Email 수신 | 외부 회신이 업무에 반영됨 | 공급사 회신과 첨부를 관련 업무·증거에 연결하고 사용자에게 도착 사실을 재입력하도록 요구하지 않는다 |
| Email 발신 | 준비된 대외 의사소통을 검토·발송 | 수신자·참조·제목·본문·첨부가 갖춰진 실제 초안을 제공하고 인간이 Send를 누르면 후속 업무를 이어간다 |
| Dashboard | 묻기 전에 운영 상황 파악 | 판단 요청, 위험, 진행, 대기, 최근 해결을 먼저 보여주고 재고 부족·소비기한·품질 보류 등 업무 위험을 확인하게 한다 |

각 채널은 동일한 업무와 역할별 담당을 보여준다. 표현 방식은 채널에 맞추되 상태·결정·근거가 달라져서는 안 된다. 채널 전환 시 업무 식별이 모호하면 필요한 대상만 확인한다. 사용자가 Case ID를 기억하는 것을 기본 전제로 삼지 않는다.

대시보드의 중심은 운영 인지다. 임의 분석·리포트는 대화에서 요청하는 경험을 목표로 하며, 현재 첫 데모의 제품명/SKU 재고 조회 범위와 구분한다. 실행 진단은 엔지니어링·관리 화면에서 제공한다.

### 5.1.2 인간에게 요청하는 판단의 형태

인간의 주의를 요청하는 사유는 권한 필요, 정책만으로 선택할 수 없는 판단, 인간만 아는 맥락, 외부 발송, 중대 예외로 구분한다. 시스템이 처리할 수 있는 조사와 초안 준비를 수행한 뒤, 업무를 진행하는 데 필요한 가장 작은 질문을 한다.

예를 들어 “이 업무를 어떻게 처리할까요?” 대신 “고객 A의 출시 납품이 고객 B보다 계약상 우선합니까?”를 묻고, 이번 배분에만 적용할지 더 넓은 정책인지 기록한다. 이미 알려진 근거를 사용자가 다시 모으게 하지 않는다.

발주 승인 요청의 예시는 다음과 같다. 수치는 UX 설명용 가상 값이다.

> Amaretti 600케이스 생산에 필요한 원재료 구매 승인이 필요합니다. 현재 전망으로는 10월 11일 완제품 품절이 예상됩니다. 제안한 원재료 발주의 약정 금액은 840만 원입니다. 품목별 수량·공급처·단가와 생산 소요량 근거를 검토한 뒤 승인하거나 반려할 수 있습니다. 발주 이후 생산과 입고는 별도 후속 업무로 남습니다.

승인이나 발송은 해당 행위를 허용하는 결정이다. 이후 추적·확인·종결 책임까지 사람에게 넘기는 것으로 처리하지 않는다.

## 7. 업무 규칙과 데이터 요구사항

### 7.1 승인 규칙

조회에는 변경 승인을 요구하지 않는다. 조회 권한 검사는 별개다.

| 변경 | 필수 승인 역할 |
|---|---|
| 발주 생성 | MANAGER |
| 입고 차단·보류 변경 | QC |
| 리콜 생성 | ADMIN |
| 생산 LOT 상태를 RECALLED로 변경 | ADMIN |

승인 전 발주안은 변경 요청으로 보관하고 승인 대상 ERP 쓰기를 먼저 실행해서는 안 된다. 승인 이벤트 수신 또는 Case 생성만으로 ERP 변경 권한이 생기지 않는다. 입고 초기 HOLD와 이후 상태 전이의 세부 규칙은 `02_flow.md`와 일치시켜야 한다.

### 7.2 데이터 불변 조건

- 공급업체 → 발주 → 발주 상세 → 입고 → 원재료 LOT → 생산 투입 → 생산 LOT → 출고 LOT → 출고 → 수주 → 고객의 추적 관계를 유지한다. 생산가공기록과의 연결은 기존 흐름도·ERD를 따른다.
- 출고 LOT별 수량 합은 출고 수량과 같아야 한다.
- 원재료 생산 투입 시 잔여 수량을 차감하고 음수를 허용하지 않는다.
- 서로 다른 Case의 업무·증거·이벤트를 잘못 연결하지 않는다.
- 이미 종료된 업무를 무관한 이벤트로 다시 실행하지 않는다.
- 감사 기록과 이벤트의 정정은 원본 덮어쓰기 대신 추적 가능한 추가 기록으로 남긴다.

## 9. 첫 데모의 완료 판정 — 제안

다음 시나리오를 준비된 예시 데이터로 모두 재현해야 첫 완결 데모가 끝난 것으로 본다.

1. 제품 재고를 조회해도 Case가 생성되지 않는다.
2. 재보충 목표를 등록하면 식별 가능한 Case와 담당 업무가 생성된다.
3. 부족량과 발주안에서 사용한 수치와 근거를 확인할 수 있다.
4. 승인 전에는 발주 쓰기가 반영되지 않는다.
5. MANAGER 승인 후 발주가 한 번만 반영되고 결과·결정·감사 이력이 연결된다.
6. 반려·무권한 승인·중복 요청에서 잘못된 발주가 생성되지 않는다.
7. 승인 대기 중 재시작해도 업무가 유지되고 승인 후 이어진다.
8. 실행 오류가 발생하면 사용자에게 필요한 조치가 표시되고 완료로 처리되지 않는다.

UX 관점에서도 다음을 확인한다. Auth0로 인증된 ChatGPT·Codex의 대화/MCP 표면에서 검증하며 Slack·Email·Dashboard의 실제 연동 완료는 첫 데모에 포함하지 않는다.

9. 사용자가 ERP 명령 순서나 내부 업무 객체를 지정하지 않고 재보충 목표를 맡길 수 있다(UX-01·02).
10. 새 대화에서 기존 업무를 다시 불러와 담당·현재 상황·대기 사유를 확인할 수 있다(UX-03·04).
11. 승인 요청만 읽어도 필요한 권한, 제안, 근거, 미조치 영향을 이해하고 근거 상세를 확인할 수 있다(UX-05·08).
12. 승인 후 추가 진행 명령 없이 처리를 이어가며, 발주 등록 완료와 장기 품절 방지 목표의 미완료를 구분한다(UX-06·12).

후속 UX 검증에서는 채널 간 동일 업무 해소, 수량 대안 비교, 정정의 다음 대화 반영, 인간 Send 이후 재개, 위험과 정상 대기를 구분하는 대시보드, 요청형 보고서의 출처 확인까지 검증한다(UX-03·07·09·10·11 및 채널별 확장).

첫 데모의 거래 조건과 수요는 시뮬레이션 데이터임을 표시한다. 실제 발주 전송·납품·매출 효과는 이 완료 판정에 포함하지 않는다.

## 10. 현재 위치와 권장 구현 순서

현재는 **업무를 접수하고 상태를 저장하며, 이벤트를 받아 다음 실행을 예약하는 기반**이 있다. 실제 AI가 업무를 수행하고, 사람이 승인하고, ERP 변경 결과를 검증하는 연결은 후속 구현이다.

| 단계 | 결과물 | 상태/제안 |
|---|---|---|
| A. 업무 데이터와 접수 기반 | ERP·업무 스키마, 재고 조회, Case 접수, 이벤트 판정 | 기존 구현 범위 |

기존 로드맵은 레이어별 개발 계획이다. 이 순서는 사용자 업무 하나가 끝나는지 확인하기 위한 묶음이며, 기존 Phase 번호를 변경하지 않는다.

### 검증 범위

- `mcp-server`: `npm test` 4개 통과. HTTP 모의 서버를 사용하는 커넥터 계약 테스트이며 실제 ERP 연동 검증은 아니다.
- `backend`: `./gradlew test --tests '*WaitingConditionMatcherTest' --no-daemon` 통과. 대기조건 판정 단위 테스트 범위다.
- DB 통합 테스트, 재시작 복구, 실제 모델 실행, 사람의 승인에서 ERP 반영까지의 전체 흐름은 이번 대조에서 실행하지 않았다.

### 우선 해소할 차이

1. 첫 데모의 구매 대상과 부족량 산정 경로를 확정한다.
2. 목표 접수 이후 실제 실행·대기·종료를 연결하고 승인과 발주 적용을 구현한다.
3. 새 대화에서 같은 업무의 담당·대기·근거를 확인할 수 있도록 상세 조회를 연결한다.
4. 수량 불변 조건과 최신 ERP 사실 조회를 실제 변경·실행 경로에서 검증한다.

현재 구현은 첫 데모를 위한 업무 상태·이벤트 기반을 제공한다. §9의 완결 데모 및 §5.1의 전체 UX 수용 기준은 아직 충족하지 않는다.

## 14. 인증 구현 착수

`feat/replenishment-demo-auth0`에서 Auth0 JWT·현재 ERP 역할 검증, 외부 신원 테이블, `/me`, 인증된 stdio·Streamable HTTP MCP, 사용자 OBO 토큰 교환 및 Auth0 설정 도구를 구현한다. 설정과 실제 연결 시험은 [Auth0 연결 안내](11_auth0_setup.md)를 따른다.

§13의 인증·MCP 구현 경계 중 이 부분을 확장하는 작업이며, 인간의 발주 결정 API·ERP 발주 적용·실제 모델 executor의 완료를 의미하지 않는다. `GET /monitor`는 읽기 전용으로 바꾸고 내부 재판정은 허용된 worker의 dispatch API로 분리한다. 실제 Auth0/두 클라이언트 로그인·갱신은 로컬 자동 테스트와 별도 검증이 필요하다.
